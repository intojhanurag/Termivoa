1. Fetch sets the peer cookie —

A credentialed fetch to the peer sets its cookie; the next fetch sends it back.



2. Later fetch and WebSocket send it —

  
A preflighted fetch and a WebSocket to the peer both carry the same cookie.


3. Cookie survives app kill and reboot —

  
Runs by itself each time the app opens. Kill the app and open it again. Then restart the phone and open it again.
     Each open adds a line below. iPhone only: also open the peer/echo in Safari. It must show
     "received": "" (the app keeps its own cookie jar).


4. Cookie expiry —

  
The peer asks for Max-Age 30 days. To see the real expiry on iPhone: Mac Safari → Develop → your iPhone → Gate 0 →
     Storage → Cookies → __Host-gate0 on the peer host → Expires (or Network → the /set request → Cookies).
     About 7 days means the WebKit IP cap applies; about 30 days means it does not. If the peer cookie is not listed, write that down.


5. Push-woken worker sends the cookie (optional) —

  
Tap the button, allow notifications, then close the app fully within 15 seconds. A notification says if the
     worker's request carried the cookie. Open the app again to see the result here.

  


6. Two scoped workers, two push keys (optional) —

  
Registers workers at /a/ and /b/, each with its own push key, and pushes to both now. PASS when both report back.

  


7. Android MANUAL

  
In Chrome: menu → Add to Home screen → Install (it must say Install, so Chrome makes a real app). Open it from the
     Home Screen and run checks 1–6 the same way. On Android the app shares Chrome's cookies, so seeing the cookie at
     the peer's /echo in Chrome is expected there. Check 4: use chrome://inspect on a computer → the app → Application → Cookies.
